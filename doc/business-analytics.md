## 1. Обзор домена

TicketFlow — платформа онлайн-бронирования билетов на культурные, спортивные и развлекательные мероприятия. Организаторы создают события и управляют категориями мест; покупатели просматривают каталог, бронируют билеты и получают уведомления о статусе брони. Ключевая бизнес-проблема, которую решает система: исключить двойные продажи при конкурентных запросах и дать организаторам прозрачную аналитику продаж в реальном времени.

## 2. Стейкхолдеры

| Стейкхолдер | Роль | Ключевой интерес |
| --- | --- | --- |
| Покупатель | Конечный пользователь | Найти событие, забронировать билет, получить подтверждение |
| Организатор | Поставщик контента | Продать места, видеть аналитику по категориям |
| Администратор платформы | Внутренняя команда | Модерация данных, контроль корректности работы системы |

*Администратор — стейкхолдер будущих версий: роли, модерация и разграничение прав в скоуп данного проекта не входят.*

## 3. Глоссарий

| Термин | Определение |
| --- | --- |
| Мероприятие (Event) | Событие с датой, местом проведения и набором категорий билетов |
| Категория билета (TicketCategory) | Тип места (Standard, VIP и т. д.) с ценой и ёмкостью |
| Вместимость (Capacity) | Общее число мест в категории, установленное организатором |
| Остаток мест (Available) | Число мест, ещё доступных для бронирования |
| Бронь (Booking) | Резервирование N билетов одной категории конкретным покупателем; фиксирует цену категории на момент создания |
| Организатор | Пользователь с правом создавать мероприятия и просматривать продажи |
| Покупатель | Пользователь с правом бронировать и отменять билеты |

## 4. Акторы системы

| Актор | Тип | Взаимодействие |
| --- | --- | --- |
| Покупатель | Человек | Просматривает каталог, бронирует и отменяет билеты, получает уведомления |
| Организатор | Человек | Создаёт, редактирует и удаляет мероприятия; смотрит отчёты по продажам |
| Система (автомат) | Фоновый процесс | Принимает события из RabbitMQ и формирует уведомления |

## 5. Use Cases

### UC-01 — Просмотр каталога мероприятий

**Актор:** Покупатель | **Предусловие:** нет

1. Покупатель запрашивает список мероприятий (с опциональным фильтром по дате).
2. Система возвращает постранично только будущие события: название, дата, место, минимальная цена.
3. Покупатель переходит к деталям интересующего события (UC-02).

**Альт.:** нет активных событий → пустой список с соответствующим сообщением.

---

### UC-02 — Просмотр деталей мероприятия

**Актор:** Покупатель | **Предусловие:** мероприятие существует (статус не `Deleted`)

1. Покупатель выбирает событие.
2. Система отдаёт полное описание, дату, место и список категорий билетов с ценой и текущим остатком мест по каждой.

**Альт.:** мероприятие не найдено → 404 Not Found.

---

### UC-03 — Бронирование билетов

**Актор:** Покупатель | **Предусловие:** в категории есть свободные места

1. Покупатель указывает категорию билета и количество (1–10 за один запрос).
2. Система атомарно проверяет и уменьшает остаток мест в Redis.
3. Система сохраняет бронь со статусом `Confirmed` в PostgreSQL.
4. Система публикует событие `BookingCreated` в RabbitMQ.
5. Покупатель получает номер брони и подтверждение.

**Альт.:** недостаточно мест → 409 Conflict; событие в прошлом → 422; суммарное число мест в активных бронях (Confirmed) этого покупателя на данное мероприятие превысит 10 (BR-05) → 422.

---

### UC-04 — Отмена бронирования

**Актор:** Покупатель | **Предусловие:** бронь существует, статус `Confirmed`

1. Покупатель отправляет запрос на отмену.
2. Система проверяет, что бронь принадлежит запрашивающему покупателю (по X-User-Id).
3. Система проверяет, что до начала мероприятия осталось более 24 часов.
4. Система переводит бронь в статус `Cancelled`.
5. Система атомарно возвращает места в Redis-счётчик.
6. Система публикует событие `BookingCancelled` в RabbitMQ.
7. Покупатель получает подтверждение отмены.

**Альт.:** бронь принадлежит другому покупателю → 403 Forbidden; до мероприятия менее 24 часов → 422; бронь уже отменена → 409.

---

### UC-05 — Просмотр своих броней

**Актор:** Покупатель

1. Покупатель запрашивает список своих броней с опциональным фильтром по статусу.
2. Система возвращает брони с деталями события, категории, количества и статуса.

---

### UC-06 — Создание мероприятия

**Актор:** Организатор

1. Организатор передаёт название, описание, дату, место и минимум одну категорию билетов (название, цена, кол-во мест).
2. Система валидирует данные и создаёт событие.
3. Система инициализирует счётчики остатков мест в Redis для каждой категории.

**Альт.:** дата в прошлом → 422; нет ни одной категории → 422; кол-во мест ≤ 0 → 422.

---

### UC-07 — Редактирование мероприятия

**Актор:** Организатор | **Предусловие:** мероприятие существует, дата в будущем

1. Организатор изменяет поля события или параметры категории.
2. Система валидирует: нельзя уменьшить вместимость категории ниже числа уже проданных мест.
3. При изменении вместимости система пересчитывает Redis-счётчик остатка.
4. Система инвалидирует кэш Redis для этого события.

**Альт.:** попытка уменьшить вместимость ниже проданных → 422; мероприятие уже прошло → 422.

---

### UC-08 — Удаление мероприятия

**Актор:** Организатор

1. Организатор запрашивает удаление мероприятия.
2. Система проверяет отсутствие активных броней (`Confirmed`).
3. Система помечает событие как `Deleted` и удаляет Redis-ключи.

**Альт.:** есть активные брони → 409 Conflict.

---

### UC-09 — Отчёт по продажам

**Актор:** Организатор

1. Организатор запрашивает отчёт по конкретному событию.
2. Система возвращает по каждой категории: продано мест, доступно мест, выручка (цена × продано), итого по событию.

---

### UC-10 — История уведомлений

**Актор:** Покупатель (пассивный) | **Триггер:** `BookingCreated` / `BookingCancelled`

1. Notification Service получает сообщение из RabbitMQ.
2. Сервис формирует текст уведомления и сохраняет в БД (`NotificationLog`).
3. По запросу покупателя система возвращает историю его уведомлений.

**Альт.:** ошибка обработки → повтор (retry); превышены попытки → сообщение в Dead Letter Queue.

## 6. Бизнес-правила

| ID | Правило | Нарушение → |
| --- | --- | --- |
| BR-01 | Дата мероприятия должна быть в будущем | 422 |
| BR-02 | Мероприятие должно иметь ≥ 1 категорию с количеством мест > 0 | 422 |
| BR-03 | Бронирование доступно только для будущих мероприятий | 422 |
| BR-04 | Нельзя забронировать больше доступного остатка мест в категории | 409 |
| BR-05 | Суммарное число мест в бронях со статусом Confirmed у одного покупателя на одно мероприятие не может превышать 10 | 422 |
| BR-06 | Отмена брони доступна не позднее чем за 24 часа до начала | 422 |
| BR-07 | Нельзя удалить мероприятие с активными бронями (`Confirmed`) | 409 |
| BR-08 | При отмене брони места возвращаются в остаток атомарно | — |
| BR-09 | Нельзя уменьшить вместимость категории ниже числа уже проданных мест | 422 |
| BR-10 | Уведомление отправляется при каждом изменении статуса брони | — |
| BR-11 | Нельзя изменить дату мероприятия, если существуют брони со статусом Confirmed | 422 |

## 7. Статусные модели

### Бронирование (Booking)

| Из статуса | Событие | В статус | Кто инициирует |
| --- | --- | --- | --- |
| — | Успешное бронирование | `Confirmed` | Покупатель |
| `Confirmed` | Отмена за ≥ 24 ч до события | `Cancelled` | Покупатель |
| `Confirmed` | Дата мероприятия прошла | `Completed` | Система (будущее) |

Возврат мест в остаток происходит только при переходе `Confirmed → Cancelled`.

*Статус `Pending` намеренно отсутствует: система переходит сразу в `Confirmed` при успешной атомарной проверке Redis. Это упрощение исключает паттерн Saga и тайм-ауты незавершённых броней — оправданно для данного скоупа.*

### Мероприятие (Event)

| Из статуса | Событие | В статус | Кто инициирует |
| --- | --- | --- | --- |
| — | Создание | `Active` | Организатор |
| `Active` | Дата мероприятия прошла | `Finished` | Система (будущее) |
| `Active` | Удаление при нулевых активных бронях | `Deleted` | Организатор |

Мероприятие в статусе `Deleted` не возвращается; `Finished` — только для чтения.

*Статус `Draft` намеренно отсутствует: мероприятие становится `Active` сразу при создании. Двухшаговая публикация организатором не входит в скоуп данной версии.*

## 8. Нефункциональные требования

| Категория | Требование | Обоснование |
| --- | --- | --- |
| Корректность | Двойная продажа на одно место недопустима даже при параллельных запросах | Ключевой риск для бизнеса организатора |
| Консистентность данных | В штатном режиме остаток мест в Redis совпадает с числом активных броней в PostgreSQL; кратковременное расхождение при сбое между шагами 2 и 3 (Redis DECRBY / PG INSERT) устраняется синхронизацией счётчиков при перезапуске сервиса | Источник правды — PostgreSQL; Redis — ускоритель |
| Аудит | Все смены статуса брони логируются с временной меткой и actor ID | Нужно для разбора конфликтных ситуаций |
| Доступность каталога | Каталог мероприятий доступен даже при недоступности Booking Service | Разделение сервисов оправдано бизнесом |
| Скорость уведомления | Уведомление доставляется покупателю не позднее чем через 5 секунд после события | SLA ожидания подтверждения |
| Наблюдаемость | Каждый запрос трассируется через `X-Correlation-ID` во всех трёх сервисах | Необходимо для диагностики ошибок в микросервисной среде |

## 9. Ограничения и допущения

**Что не входит в скоуп:**

- Оплата и платёжные шлюзы — факт бронирования приравнивается к «оплате»
- Реальная аутентификация/авторизация — `UserId` передаётся в заголовке `X-User-Id`
- Отправка email/SMS — уведомление = запись в таблице `NotificationLog`
- Роли и разграничение прав — Покупатель и Организатор различаются только по передаваемому заголовку
- Мультивалютность — одна валюта без конвертации

**Допущения:**

- Один покупатель идентифицируется по `UserId` (GUID), без верификации личности
- Организатор может управлять только своими мероприятиями (проверка по `OwnerId` без JWT)
- Временно́е окно «24 часа до отмены» считается по UTC
- Система не обрабатывает частичные возвраты: отмена — это всегда вся бронь целиком
